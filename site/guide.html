Install

curl -fsSL https://swx.quadratic.xyz/install.sh | sh

The script downloads the release for your OS and CPU, checks it against the release's SHA256SUMS, and installs swx and swift-x into ~/.local/bin. With swift-x on your PATH, swift x build works too. SWX_VERSION=v0.1.0 pins a release and SWX_INSTALL_DIR changes the location. swx self update later replaces the binary with the newest release, checked the same way (--version picks one, --check only asks).

With Homebrew, the repository is its own tap; with Mint, swx builds from source:

brew tap jeslyvarghese/swx https://github.com/jeslyvarghese/swx
brew install swx                 # and later: brew upgrade swx
mint install jeslyvarghese/swx

From source, with Swift 6.1 or later:

git clone https://github.com/jeslyvarghese/swx && cd swx
swift build -c release
cp .build/release/swx ~/.local/bin/
ln -s swx ~/.local/bin/swift-x   # optional: enables `swift x …`

swx runs SwiftPM for builds, so a Swift toolchain must be installed (or let swx toolchain install fetch one).

Dependencies

swx add goes from a name to a resolved dependency in one step, like uv add. It finds the package (a URL, owner/repo, or a name from the Swift Package Index), picks its newest release and the right library, adds both to Package.swift through SwiftPM's own editor, and resolves. 

swx add swift-argument-parser             # .package(…, from: "1.8.2") + ArgumentParser on your target
swx add swift-nio@2.60.0 --product NIOCore
swx add apple/swift-log --target Server
swx add https://github.com/me/kit --branch main

swx remove takes a dependency out again, with every target's use of its products. swx upgrade moves requirements that exclude a dependency's newest release to it, keeping each requirement's form; updates within your requirements are swx package update. Both edit only what they must and leave the rest of Package.swift as you wrote it, then resolve; if the new versions don't resolve together, upgrade puts the manifest back. 

swx remove swift-nio
swx upgrade --dry-run          # swift-argument-parser: would move 0.4.0 → 1.8.2
swx upgrade swift-argument-parser

Resolving is a drop-in for swift package resolve and update, with the same flags. Any other package subcommand is forwarded to SwiftPM.

swx package resolve
swx package resolve --check     # exit 1 if resolving would change Package.resolved (for CI)
swx package update
swx package show-dependencies   # SwiftPM's output, without SwiftPM (see Graphs)
swx package dump-package        # forwarded to `swift package`

The result is what SwiftPM would have written: the same Package.resolved, the same .build/checkouts and .build/workspace-state.json. A later swift build finds everything resolved and does no network work.

Graphs

swx graph shows what your targets depend on, like tuist graph: your targets, the products they use from each package with its pinned version, and the platform and trait conditions on each edge. It follows SwiftPM's rules, so dependencies switched off by traits don't appear. 

$ swx graph
App (executable)
├── AsyncAlgorithms · swift-async-algorithms 1.1.7 (library product)
├── Logging · swift-log main (library product) [linux, macos]
└── Local · local (library product)
AppTests (test)
└── App (executable) (*)
swx graph --level package                  # one node per package
swx graph --external targets --focus App   # all App reaches, down to dependencies' targets
swx graph --skip-tests --external none     # only this package's own targets
swx graph --format mermaid                 # renders in GitHub comments and READMEs
swx graph --format json                    # packages, nodes and edges, for tools
swx graph -o graph.svg                     # drawn by Graphviz (.svg, .png, .pdf)

(*) marks a node whose dependencies are already shown above. Image output needs Graphviz's dot; --format dot prints the same graph as text.

swx package show-dependencies prints exactly what SwiftPM prints, in all four of its formats (text, dot, json, flatlist), without starting SwiftPM: 17 ms instead of 359 ms for Vapor's 32 packages. Where SwiftPM swaps swift-syntax for its prebuilt libraries (macros, and the tests of macros), swx drops it from the graph by the same rules. Graphs with edited packages go to SwiftPM itself. SwiftPM lists two or more traits of a package in a different order on every run; swx sorts them.

Inspecting

Questions about the resolved graph, each answered from local data except where noted.

swx why swift-collections   # who depends on it, up to the root
swx outdated                # pinned, wanted (what your requirements allow) and latest versions
swx audit                   # known vulnerabilities (GitHub's advisory database, via OSV.dev); exit 1 if any
swx licenses                # each dependency's license (SPDX); --format csv for compliance tools
swx inspect imports         # undeclared imports (exit 1) and unused dependencies

swx inspect imports catches the bug that works locally and fails in a clean build: a target importing a module it doesn't declare, which only links because something else pulled it in. It parses every target's sources, in every #if branch, and suggests the product to declare. outdated and audit list versions and advisories over the network; all of them take --format json.

For CI, .swx/policy.json says what to accept: advisories to ignore (by GHSA or CVE id, still named in the report), the mildest severity that fails audit (unrated advisories always fail), and when outdated fails: never (the default), wanted (the lockfile is behind your requirements) or latest (any newer release). --ignore adds to the file and --fail-on overrides it. 

{
  "audit": { "ignore": ["GHSA-xvr7-p2c6-j83w"], "failOn": "high" },
  "outdated": { "ignore": ["swift-syntax"], "failOn": "wanted" }
}

Publishing

swx publish is swift package-registry publish: the same arguments, the same archive (the package without .build, .git, .gitignore and .swiftpm, zipped under <scope>.<name>/), the same signatures and the same request. package-metadata.json is sent when the package has one. 

swx publish mona.LinkedList 1.2.0 --url https://registry.example.com
swx publish mona.LinkedList 1.2.0 --private-key-path key.p8 --cert-chain-paths leaf.der intermediate.der root.der
swx publish mona.LinkedList 1.2.0 --signing-identity "Mona Signer"                # a Keychain identity (macOS)
swx publish mona.LinkedList 1.2.0 --dry-run --scratch-directory out   # archive and signatures, no upload
swx publish mona.LinkedList 1.2.0 --wait 600                          # follow an asynchronous registry to the outcome

With a key and certificate chain, the manifests in the archive, the archive and the metadata are signed (cms-1.0.0, as SE-0391 defines). The registry is --url, or the one registries.json configures for the scope; credentials come from the netrc file or the Keychain, as for resolving. On macOS, --signing-identity "Label" signs with a Keychain identity instead, without the key ever leaving the Keychain.

Build, test, run

swx resolves first, then hands over to SwiftPM with resolution disabled.

swx build -c release
swx test
swx run MyTool --flag

SWX_BUILD_CACHE=1 shares compiled dependencies between projects through the compiler's content-addressed cache (with SwiftPM's native build system): a second project that uses swift-collections built in 1.7 s instead of 6.4 s.

swx test --selective runs only the test targets whose inputs changed since they last passed: their sources and those of the targets they depend on, the manifest, the pins, path dependencies, the toolchain and the test arguments. When nothing changed, nothing runs. Passing results are kept in the store, so the remote cache shares them between machines.

Monorepos

--all runs a command for every package under --package-path (the current directory by default), nested ones included, skipping .build, hidden directories and packages that swift package edit put in Packages/. Each package gets the files SwiftPM would write for it, and all of them share one store, so a repository used by several packages is fetched once. 

swx package resolve --all          # four at a time; each result under its package's path
swx package resolve --check --all  # exit 1 naming every stale Package.resolved
swx package update --all
swx build --all                    # one package after another
swx test --all --selective
swx cache pull --all && swx cache push --all

To choose the packages, .swx/workspace.json at the root lists globs of package directories to cover and to leave out (* within a path component, ** across them, . for the root): 

{ "packages": ["Packages/**", "."], "exclude": ["**/Examples/**"] }

Caches

Everything swx downloads or builds lives in one store (~/.cache/swx), shared by every project. swx cache size shows what it holds. swx cache prune removes what no project resolved with swx still pins and nothing used within --older-than (30 days by default), plus scratch left by interrupted runs. Projects keep working: their checkouts are copies, so only a fresh checkout of a removed entry fetches it again. 

swx cache size
swx cache prune --dry-run
swx cache prune --older-than 7d

swx cache push and pull share the store with other machines: the source tree and manifests of every pinned commit, the binary artifacts the manifests declare, and the results of swx test --selective. After a pull, resolving restores every checkout without running git.

With --build they also share .build, without the checkouts swx restores itself. SwiftPM reuses build outputs only at the same absolute path with the same toolchain, which CI runners keep stable, so both are part of the key. A pull restores the archive built from exactly these files, else one built with the same Package.resolved, whose dependencies are still current; it never overwrites an existing build. A release build of a package using swift-argument-parser, swift-collections and swift-nio took 23 s cold and 3 s after a pull into an empty store. With SwiftPM's native build system, the sample package took 11 s cold and 1 s restored.

The path is not something swx can hide. SwiftPM's build system records the package's real path, symlinks resolved, in what it builds from, so a checkout elsewhere rebuilds everything; a stable symlink would only help the deprecated native build system. On laptops, the store still saves the downloads and checkouts.

Remote caches grow too: swx cache size --remote … totals them by kind, and swx cache prune --remote … --older-than 30d deletes the files swx wrote that were last uploaded (in a directory remote, last downloaded) before then; the next push uploads what a project still needs. HTTP remotes can't be listed, so expire their files on the server. $SWX_REMOTE_CACHE is never used for a prune: name the remote. 

# CI: restore, resolve offline, test what changed, share the results
export SWX_REMOTE_CACHE=s3://my-bucket/swx
swx cache pull --build
swx package resolve
swx test --selective
swx cache push --build
RemoteCredentials
a directory or file:///…none (a mounted drive, or a folder CI caches)
https://host/prefixGET, HEAD and PUT; SWX_REMOTE_CACHE_TOKEN as a bearer token
s3://bucket/prefixAWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_REGION; SWX_S3_ENDPOINT for R2 or MinIO

CI

The repository is also a GitHub Action that installs swx. A workflow that fails on stale lockfiles, vulnerable dependencies and undeclared imports, and shares checkouts, builds and test results between runs: 

jobs:
  check:
    runs-on: macos-26
    env:
      SWX_REMOTE_CACHE: s3://my-bucket/swx
      AWS_ACCESS_KEY_ID: ${{ secrets.AWS_ACCESS_KEY_ID }}
      AWS_SECRET_ACCESS_KEY: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
      AWS_REGION: eu-west-1
    steps:
      - uses: actions/checkout@v4
      - uses: jeslyvarghese/swx@v0.6.0      # with: version: v0.6.0 (default: latest)
      - run: swx cache pull --build
      - run: swx package resolve --check    # Package.resolved is committed and current
      - run: swx audit                      # honours .swx/policy.json
      - run: swx inspect imports
      - run: swx test --selective
      - if: always()
        run: swx cache push --build

Without a bucket, point SWX_REMOTE_CACHE at a directory that actions/cache saves and restores.

Apple platforms

Packages that declare apps with AppleProductTypes (.iOSApplication(…), as Xcode and Swift Playgrounds read them) build, run and test on simulators and devices. swx uses xcodebuild, simctl and devicectl underneath, so this needs macOS with Xcode. 

swx devices                                       # simulators and paired devices
swx build --platform ios                          # generic build when no simulator exists
swx run   --platform ios HelloApp                 # build, install, launch, stream console
swx run   --hot --platform ios HelloApp           # …and reload saved edits in the running app
swx run   --platform ios --destination device --team ABCDE12345 HelloApp
swx test  --platform watchos                      # package tests on a watchOS simulator

Platforms: ios, watchos, tvos, visionos.

xcodebuild builds a package's .iOSApplication as a bare executable, so swx run builds app products from a project it generates under .build/swx-xcode (through XcodeGen); the package itself isn't touched.

Compile jobs are cached in swx's store with Xcode's compilation cache, so they outlive DerivedData: after rm -rf .build, a simulator build of a package using swift-syntax, swift-collections and swift-algorithms took 4 s instead of 17 s, on every platform. Hits need the package at the same path, which CI checkouts are. Your own COMPILATION_CACHE_ENABLE_CACHING=… wins; SWX_BUILD_CACHE=0 turns it off.

On CI the checkout path never changes, so keeping the cache between runs is enough. Keys start with the Xcode build, since a new Xcode compiles differently: 

- id: xcode
  run: echo "build=$(xcodebuild -version | tail -1 | awk '{print $3}')" >> "$GITHUB_OUTPUT"
- uses: actions/cache@v4
  with:
    path: ~/.cache/swx/cas
    key: swx-cas-${{ steps.xcode.outputs.build }}-${{ github.run_id }}
    restore-keys: swx-cas-${{ steps.xcode.outputs.build }}-
- run: swx test --platform ios

A copy at another path (a second worktree, another machine's home directory) misses: the compiler keys each job on its working directory, <package>/.swiftpm/xcode. Xcode's SWIFT_OTHER_PREFIX_MAPPINGS and CLANG_OTHER_PREFIX_MAPPINGS (<package path>=/^root, with SWIFT_ENABLE_PREFIX_MAPPING=YES and CLANG_ENABLE_PREFIX_MAPPING=YES) make those builds hit too, but #filePath and debug info then read /^root/…, which breaks tests that find fixtures or snapshots next to their sources. swx leaves that choice to you.

Hot reload

swx run --hot keeps the app running while you edit: each saved Swift file is compiled alone, with the exact flags the build used for its module, and loaded into the app, usually within a second. SwiftUI views redraw with the new code and keep their @State. Nothing in the project changes: no package, no build setting in a file, no @ObserveInjection. 

swx run --hot --platform ios HelloApp             # simulator
swx run --hot --platform macos HelloApp           # this Mac

How: the build adds -Xlinker -interposable and testability on xcodebuild's command line (in its own DerivedData, so normal builds stay as they are), and swx inserts a small agent into the app through the environment. For each save, swx asks the Swift driver for that file's compile job, links the object into a patch, and the agent points the app's calls, vtables and witness tables at the new functions, then marks SwiftUI's view graphs stale.

Some edits can't run in a process that started with the old code, and rebuild and relaunch instead, saying why: a type's stored properties, enum cases, conformances or an open class's methods; a view's body that now returns another type of view; global and static stored properties (a patch would get a second copy); added or removed files and Package.swift. A compile error is shown and waits for the next save.

Simulators and this Mac for now, not devices. Apps with the hardened runtime don't load the agent and run without hot reload.

Xcode projects

Xcode's own resolution can't be replaced, but it can be fed. swx xcode resolve prepares SourcePackages exactly as Xcode would (same pins, originHash and state), including projects with registries, mirrors and local package folders. 

swx xcode resolve --source-packages SourcePackages
xcodebuild -clonedSourcePackagesDirPath SourcePackages \
           -disableAutomaticPackageResolution -onlyUsePackageVersionsFromResolvedFile …

When an app outgrows a package, swx xcode generate writes an .xcodeproj for its .iOSApplication products (through XcodeGen, fetched like any swx tool).

Toolchains

swift.org releases and snapshots, installed per user. Every command honours .swift-version and installs the pinned toolchain on demand.

swx toolchain list --available
swx toolchain install 6.4
swx toolchain install main-snapshot   # also 6.5-snapshot, or a snapshot tag
swx toolchain use 6.4                 # writes .swift-version
swx toolchain which

Tools

Run executables from packages without installing them, like uvx or Mint. Builds are cached per revision and toolchain, so a pinned tool starts in about 20 ms.

swx tool run swiftformat@0.54.0 --version
swx tool run realm/SwiftLint lint
swx tool install swiftlint     # links into ~/.local/bin

Scripts

Single-file scripts declare their dependencies in a comment; products are inferred from the imports. A warm start takes about 10 ms.

#!/usr/bin/env -S swx run
// swx-dependencies:
// .package(url: "https://github.com/apple/swift-argument-parser", from: "1.3.0")

import ArgumentParser
swx run greet.swift Ada

Compatibility

Each of these is checked byte for byte against SwiftPM or Xcode:

  • Package.resolved: v2 and v3 written, v1 read; originHash matches SwiftPM's and Xcode's.
  • Workspace state: workspace-state.json v7, including path dependencies, binary artifacts (local ones recorded in place) and prebuilts. Entries swx doesn't manage (edited packages) are kept untouched.
  • Prebuilt swift-syntax: as SwiftPM 6.4 does while resolving, the signed prebuilts manifest for this compiler and SDK is checked against Apple's roots, and the libraries are downloaded once per machine, checksum-verified and placed in .build/prebuilts. --disable-experimental-prebuilts turns it off.
  • Dependencies: branch, revision, path and local git dependencies; SwiftPM's pruning, traits, tag-to-version rules and pre-release ranges.
  • Mirrors: mirrors.json from the package and ~/.swiftpm; the original URL is what the lockfile records.
  • Submodules and Git LFS: checked out as SwiftPM checks them out (LFS needs git-lfs, as SwiftPM does).
  • Registries: registries.json, SwiftPM's credential lookup (environment, Keychain, .netrc), checksums and trust-on-first-use fingerprints, SE-0391 signatures, and --replace-scm-with-registry.
  • Tag fingerprints: the commit behind each tag is recorded in SwiftPM's store, and a tag that moves is refused.
  • Binary targets: XCFrameworks, artifact bundles and .artifactbundleindex, downloaded and unzipped once per machine; local ones used in place, and local zips extracted and recorded with their checksum. A local zip that changes while the lockfile and checkouts stay current is picked up by the next swift package resolve, not by swx's no-op.
  • Manifests: 0 disagreements with dump-package over a 364-manifest corpus, and SwiftPM's tools-version rules, including that a version below 6.0 must be on the first line.
  • Publishing: the archive, signatures and request of swift package-registry publish.
  • Xcode: projects, workspaces and root package folders, with the registries and mirrors Xcode keeps in xcshareddata.
  • Mixed use: swift package update works on top of swx checkouts, and swift-syntax prebuilts still apply.

Multi-root workspaces are not supported.

Verification

Compatibility is checked differentially: each script runs SwiftPM or Xcode and swx on the same input and compares what they write. The full list is in the contributing guide; for example: 

Scripts/compare-with-swiftpm.sh <package-dir>   # Package.resolved, workspace-state.json, checkouts
Scripts/compare-registry-signing.sh             # signed registry releases: trusted, untrusted, tampered
Scripts/compare-xcode-apps.sh                   # an app + widget + watch app project vs xcodebuild
Scripts/check-manifest-edits.sh                 # add, remove, upgrade, each resolved like SwiftPM
Scripts/compare-corpus.sh <dir>                 # 206 popular packages: 200 identical, 6 refused by both
Scripts/compare-registry-publish.sh             # swx publish vs swift package-registry publish
Scripts/check-monorepo.sh                       # --all on a monorepo, each package vs SwiftPM
swx debug manifest-parity --cache-path <dir>    # the static parser vs dump-package over a corpus

Found a difference from SwiftPM? That's a bug — please report it.
